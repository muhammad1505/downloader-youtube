## R1 — P2: Kepemilikan cleanup belum terlindungi penuh (BUG-002/004)

**Lokasi:** [DownloadWorker.kt](../app/src/main/java/id/local/tubeflow/core/DownloadWorker.kt), 215–222; [Models.kt](../app/src/main/java/id/local/tubeflow/core/Models.kt), 76; [DownloadViewModel.kt](../app/src/main/java/id/local/tubeflow/core/DownloadViewModel.kt), 96, 205–211, 220–225, 281, 401–403.

Token `generation` melindungi mutasi status worker lama. Namun `takenOverByOther()` dihitung sekali sebelum cleanup dan `dao.clearPending(jobId)` tidak memakai generasi. Jika resume/worker baru masuk setelah pemeriksaan itu, worker lama dapat menghapus jejak URI pending milik generasi baru; penghapusan direktori juga berbagi path job yang sama. `cancelOne` mengandalkan status WorkManager, sementara `remove`/`clearUnsuccessful` menghapus direktori langsung.

Simulasi dengan schema/SQL DAO asli: resume generasi 0→1, worker baru mencatat pending, kemudian SQL `clearPending` lama menghasilkan `('RUNNING', 1, NULL)`. Ini membuktikan update lama tidak dibatasi kepemilikan; urutan coroutine lengkap belum diuji di perangkat. WorkManager mendokumentasikan pembatalan sebagai best-effort, sehingga finished/cancelled bukan bukti semua eksekusi selesai. [Referensi WorkManager](https://developer.android.com/reference/androidx/work/WorkManager.html).

**Arah perbaikan:** Buat cleanup bersyarat generasi dan koordinasikan engine/direktori melalui kepemilikan yang sama; tunggu eksekusi pemilik benar-benar selesai sebelum menghapus parsial. Jangan menganggap kegagalan membaca WorkManager sebagai aman untuk delete.

- [ ] Uji terkontrol: worker lama memasuki cleanup, resume berjalan, worker baru membuat pending; URI/status/berkas generasi baru tetap utuh.
- [ ] Uji cancel/remove/clear saat engine belum selesai berhenti, termasuk retry cepat dan restart.

## R2 — P2: Jejak URI sidecar masih bisa hilang (BUG-008)

**Lokasi:** [DownloadWorker.kt](../app/src/main/java/id/local/tubeflow/core/DownloadWorker.kt), 183–185, 282–298; [DownloadViewModel.kt](../app/src/main/java/id/local/tubeflow/core/DownloadViewModel.kt), 83–89, 367–394.

Setelah sidecar terbit, `publishSidecars` menghapus URI dari `sidecarPending`, tetapi `sidecarUris` baru disimpan setelah fungsi selesai. Proses mati di antara kedua langkah meninggalkan file terbit tanpa jejak. Simulasi SQL pada baris completed menghasilkan `(COMPLETED, sidecarUris=NULL, sidecarPending=NULL)` pada jendela ini; filter recovery tidak akan memilih baris tersebut.

Pada kegagalan, hasil `StorageUris.delete` juga diabaikan sebelum pending dihapus dari database. Jika provider/izin menolak penghapusan, file masih ada tetapi recovery kehilangan URI. Jalur `writeLyricBesideAudio` membuat/menulis sidecar baru tanpa jurnal pending, sehingga copy yang terputus oleh proses mati masih dapat tertinggal.

**Arah perbaikan:** Commit URI terbit dan penghapusan pending dalam satu transaksi per sidecar. Pertahankan pending bila delete gagal. Gunakan jurnal yang sama pada cari ulang lirik dan recovery; setelah rename, perbarui URI karena provider dapat mengubah document ID. [Referensi DocumentsContract](https://developer.android.com/reference/android/provider/DocumentsContract).

- [ ] Simulasikan proses mati setelah create, setelah rename, saat write, dan setelah publish sebelum commit; semua URI tetap dapat ditemukan/ditindaklanjuti.
- [ ] Delete gagal tidak menghapus jejak pending; retry cleanup setelah izin/provider pulih berhasil.

## R3 — P2: Lirik versi berbeda masih diterima (BUG-013)

**Lokasi:** [Lyrics.kt](../app/src/main/java/id/local/tubeflow/core/Lyrics.kt), 105–120, 136–155, 212–213; [DownloadWorker.kt](../app/src/main/java/id/local/tubeflow/core/DownloadWorker.kt), 109–122.

Probe memanggil **kelas aplikasi hasil build** dengan handler HTTP lokal buatan: semua respons berisi kandidat studio `Song`, artis `Artist`, durasi 200 detik. Tidak ada request lagu nyata ke LRCLIB.

```text
RAW_LIVE_SCORE=-1.0
LIVE_REQUEST_STUDIO_RESULT=tersimpan; CALLS=4
DURATION_200_VS_229_SCORE=1.0
UNKNOWN_ARTIST_AND_DURATION_SCORE=1.0
```

`LyricMatch` memang menolak query `Song (Live)` terhadap studio. Tetapi `Lyrics.fetch("Artist - Song (Live)", 200)` membuat fallback `tidy` yang menghapus semua isi tanda kurung, membangun query baru `Song`, lalu menerima versi studio. Tes yang hanya memanggil `LyricMatch.score` tidak mencakup bypass ini.

Gerbang durasi memakai `max(20 detik, 15%)`; 200 vs 229 detik diterima dengan skor 1.0. Perbedaan sebesar itu belum aman untuk sinkronisasi. Query tanpa artis/durasi juga dapat menerima artis lain dengan skor 1.0. Saat worker memperoleh metadata untuk judul placeholder, ia hanya memperbarui judul, bukan `durationSeconds`, sehingga job seperti ini tetap kehilangan gerbang durasi. LRCLIB mendokumentasikan pencocokan durasi ±2 detik pada get; durasi dekat pun tidak menyelaraskan intro video secara otomatis. [Dokumentasi LRCLIB](https://lrclib.net/docs).

**Arah perbaikan:** Normalisasi kata promosi tanpa menghapus identitas versi. Nilai semua kandidat terhadap identitas asli yang tetap; kirim durasi ke API saat valid dan terapkan kebijakan sinkronisasi yang ketat. Persist durasi hasil inspeksi worker. Kandidat dengan identitas yang belum dapat diverifikasi memerlukan pemilihan manual atau hasil meragukan, bukan skor penuh otomatis.

- [ ] Tambahkan tes end-to-end `Lyrics.fetch` dengan fixture Live/remix/studio; seluruh fallback tetap menolak versi salah.
- [ ] Uji durasi berbeda puluhan detik dan metadata kosong; jangan menganggap sinkron sebelum memeriksa playback awal/tengah/akhir.

## R4 — P2: Kegagalan parsial pencarian menjadi “tidak ditemukan” (BUG-014)

**Lokasi:** [Lyrics.kt](../app/src/main/java/id/local/tubeflow/core/Lyrics.kt), 146–147, 178–201.

Probe: get mengembalikan 404, search by-field mengembalikan `[]`, dan free search mengembalikan 503. Hasil aktual:

```text
GET_404_SEARCH_EMPTY_FREESEARCH_503=tidak_ditemukan; CALLS=3
```

Satu respons 200 menyalakan `sawResponse`, sehingga kegagalan jalur pencarian lain diabaikan pada keputusan status. Pengguna diberi kesan pencarian lengkap tidak menemukan lirik, padahal salah satu pencarian tidak berhasil.

**Arah perbaikan:** Bila belum ada kandidat dan jalur pencarian yang diperlukan gagal, laporkan jaringan/pencarian belum lengkap, atau status parsial yang bisa dicoba lagi. Tes status harus memanggil pencarian dengan fixture respons; tes label status saja tidak membuktikan klasifikasi ini.

- [ ] Kombinasi 404/empty/timeout/5xx diklasifikasikan tepat; hasil yang berhasil tetap boleh dipakai jika memenuhi kriteria kecocokan.

## R5 — P2: Cari ulang dapat melaporkan sukses untuk `.lrc.txt` (BUG-015)

**Lokasi:** [DownloadViewModel.kt](../app/src/main/java/id/local/tubeflow/core/DownloadViewModel.kt), 320–324, 370–375, 390–395.

Jalur download awal memeriksa nama aktual `.lrc` sebelum menyatakan tersimpan. Pada cari ulang, bila create menghasilkan `.lrc.txt` dan rename gagal/null, fungsi memakai URI `made`, tetap menulis, mencatat URI, lalu mengembalikan `true` tanpa memeriksa nama akhir. Status menjadi `tersimpan` walaupun pemutar tidak mendapatkan nama sidecar yang sesuai. Ini adalah jalur kode bersyarat yang teridentifikasi; provider yang menolak rename belum diuji dalam sesi ini.

**Arah perbaikan:** Setelah create/rename, verifikasi nama tampilan cocok dengan stem audio dan ekstensi yang diminta sebelum sukses. Bila tidak dapat dipenuhi, laporkan gagal simpan dan jalankan cleanup terjurnal. Jangan menghapus lirik lama sebelum pengganti benar-benar valid.

- [ ] Fixture provider menambahkan `.txt` dan menolak rename: status gagal simpan, tidak ada sidecar salah nama yang diumumkan sukses.

## R6 — P2: Retry inspeksi playlist dapat mengulang inspeksi video

**Lokasi:** [DownloadScreen.kt](../app/src/main/java/id/local/tubeflow/ui/DownloadScreen.kt), 197–215; [DownloadViewModel.kt](../app/src/main/java/id/local/tubeflow/core/DownloadViewModel.kt), `inspectPlaylist`.

Untuk watch/Shorts/youtu.be + list, pengguna bisa membuka playlist lalu inspeksinya gagal. Tombol “Coba lagi” memilih `inspect()` ketika `isVideo` true, sehingga mengulang video, bukan operasi playlist yang gagal. Tombol buka playlist masih tersedia sebagai workaround; masalah retry URL sama yang awal sudah mendapat perbaikan, tetapi konteks operasi terakhir belum dipertahankan.

**Arah perbaikan:** Simpan jenis inspeksi terakhir dan gunakan saat retry, termasuk URL asli. Uji kegagalan video dan playlist untuk URL yang sama. Catatan ini melengkapi verifikasi BUG-006/007; tidak dihitung sebagai ID baru terpisah.

## R7 — P2: Penggantian lirik merusak file lama bila write gagal (BUG-016)

**Lokasi:** [DownloadViewModel.kt](../app/src/main/java/id/local/tubeflow/core/DownloadViewModel.kt), 345–349, 364–365.

`writeTo(validOld.first(), "wt")` menimpa dokumen lama langsung. Jika stream sudah membuka/truncate file kemudian write/close gagal, lirik lama telah kosong atau hanya terisi sebagian. `runCatching` mengembalikan false setelah kerusakan terjadi; komentar bahwa lirik lama tetap utuh sampai pengganti berhasil tidak sesuai dengan jalur ini. Mode truncate ditentukan lewat descriptor provider. [Referensi mode file Android](https://developer.android.com/reference/android/os/ParcelFileDescriptor#parseMode(java.lang.String)).

**Arah perbaikan:** Siapkan dan verifikasi pengganti sebelum mengganti file lama; gunakan kemampuan rename/replace provider atau backup/rollback yang diuji. Publikasi, pembaruan URI, dan cleanup harus mempertahankan data lama bila gagal. Jangan menjanjikan penggantian atomik lintas semua provider tanpa bukti.

- [ ] Simulasikan kegagalan sesudah stream terbuka, sesudah beberapa byte, dan saat close; isi/nama/URI lirik lama tetap dapat dipulihkan dan status gagal simpan ditampilkan.
